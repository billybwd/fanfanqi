# 翻翻棋 · 纯 Python 提示版

基于 [igofreely/fanfanqi](https://github.com/igofreely/fanfanqi) 的纯 Python 重写，**无任何第三方依赖**（界面使用标准库 tkinter）。

两种模式（界面「设置 → 模式」切换）：

- **录入+提示**（默认）：AI 不自己落子，给出的走法只作为“提示”。双方每一步都由使用者录入
  （例如照着实物棋盘录入，翻出什么棋子由你选择），轮到开启了提示的一方时，AI 在后台计算并给出建议。
- **人机对战**：选择执红或执黑，与电脑对弈。开局 4 个明子和之后每次翻子 / 炮打暗子的结果都**随机**
  从剩余棋子池中抽取；电脑自动走子，可选让 AI 为你提示。悔棋会退回到你上一次行动之前。

## 运行

```bash
python main.py          # 需要 Python 3.8+（自带 tkinter）
python -m tests.selfplay                              # 规则测试 + 各 AI 合法性 + V17 自对弈
python -m tests.selfplay StrategicV17AI StrategicV16AI 10 0.3 # V17 对比 V16 基准
```

## 使用方法

以下为录入模式；人机对战模式下开局自动随机放置，翻子结果随机，无需弹窗选择。

1. **开局放置**：点击黄色高亮格，在弹窗中选择该位置实际出现的明子（共 4 个固定位置）。
2. **对局录入**：
   - 点击暗子 → 在弹窗中选择实际翻出的棋子；
   - 点击己方明子 → 绿色标出可走/可吃的位置 → 点击目标；
   - 炮打暗子时，弹窗中选择被打掉的是哪枚棋子。
3. **AI 提示**（右侧面板）：轮到“提示方”时自动计算，显示建议走法、用时、决策依据
   （紧急战术覆盖 / Alpha-Beta 搜索层数与评估分），并在棋盘上用橙色虚框和箭头标出。
   V16/V17 搜到「提示起始层数」（默认 4）就先显示“当前建议（继续计算中）”，之后每加深一层更新，
   思考时间用完后显示最终建议；不必等满时间，随时可以按当前建议走。
   - 「按提示走」：直接执行建议（翻子仍需录入实际翻出的棋子）；
   - 「重新计算」：更换模型或思考时间后重新计算。
4. 设置：模式、执子方（人机对战）、AI 模型（SimpleAI ~ StrategicV17AI，默认 V17）、思考时间、
   提示方（双方/红方/黑方/关闭）。
5. 右侧「被吃掉的棋子」面板显示双方各自失去的棋子和扣掉的血量。
6. 悔棋、新对局、保存棋谱（JSON）；「导出局面 / 导入局面」读写下文的状态格式，
   可以把任意局面（例如外部识别得到的）载入后继续对局、让 AI 给提示。

## 配置文件 config.json

界面中的设置会自动保存到项目根目录的 `config.json`，下次启动沿用；也可以直接编辑（重启生效），
缺失或写错的项会回退到默认值。

| 键 | 默认 | 说明 |
|---|---|---|
| `mode` | `"record"` | `"record"` 录入+提示 / `"vs"` 人机对战 |
| `player_side` | `"red"` | 人机对战中玩家执哪一方（红方先手） |
| `ai_model` | `"StrategicV17AI"` | AI 模型 |
| `engine` | `"python"` | 搜索引擎：`"python"` 或 `"go"` |
| `go_threads` | `4` | Go 搜索线程数（根着法并行 + 共享置换表；受 CPU 逻辑核心数限制） |
| `rules.long_chase_limit` | `5` | 同一方连续追同一目标达到该次数时，必须变招 |
| `rules.no_capture_limit` | `16` | 连续未吃子普通移步达到该次数时和棋；翻棋不计步 |
| `think_time_sec` | `2.5` | 提示的思考时间（秒），对 V15、V16、V17 生效 |
| `ai_think_time_sec` | `2.5` | 人机对战中电脑走子的思考时间（秒） |
| `hint_min_depth` | `4` | V16/V17 搜到这一层就先显示提示，之后每加深一层更新，直到思考时间用完；局面一变旧计算立即停止。0 = 只显示最终结果 |
| `hint_side` | `"both"` | `"both"` / `"red"` / `"black"` / `"off"` |
| `show_hint_on_board` | `true` | 是否在棋盘上画出提示 |
| `ai_move_delay_ms` | `400` | 人机对战中电脑算完后停顿多久再落子 |
| `search.max_iterative_depth` | `7` | V15 迭代加深的最大层数上限 |
| `search.max_root_actions` | `16` | 根节点最多考虑的候选着法数 |
| `search.max_node_actions` | `8` | 内部节点最多展开的着法数 |
| `search.max_noisy_actions` | `6` | 静态搜索（只看吃子）的着法数 |
| `search.max_flip_squares` | `4` | 每个节点考虑翻哪几个暗子 |
| `search.max_pool_choices` | `2` | 每次翻子假设的翻出结果种类数 |
| `search.quiescence_depth` | `2` | 静态搜索深度 |

`search` 中的值等于原版 V15 的参数，调大更强但更慢；只作用于 StrategicV15AI。

坐标显示与原版一致：`(列,行)`，从 0 开始，棋盘边上有标注。

## AI 策略的保留情况

`ai.py` 保留原项目的 V2~V15 策略代码，供历史对照和兼容使用。它们属于一条逐版继承的旧策略链；
V15 依赖 V2~V14，因此这些版本不能独立删去。当前主策略是从头实现的 V16/V17，不继承这条旧策略链：

- V15 的旧策略链包含紧急战术覆盖（护将、防兵杀将、安全吃子 / 有利兑子、残局强制手）；
- 否则进行迭代加深 negamax + Alpha-Beta 搜索，带置换表、PV 优先、静态搜索（只看吃子）、
  对杀局面延伸搜索、按局面复杂度自适应最大深度；
- 局面评估沿用 V14 的轻量评估（HP、子力、机动性、危险、兵逼将、困将、剩余池价值等），
  走法排序与战术判断复用 StrategicV13AI 的整套启发式；V16/V17 不使用这些规则。

与原版的差异只有：

- 去掉了 Web Worker、远程 AI（RemoteAI）、神经网络推理和复盘界面；
- V15 额外记录 `last_decision_info`（决策来源、搜索深度、评估分）用于提示展示，不影响走法选择；
- Python 比浏览器中的 JS 慢不少，因此默认思考时间设为 2.5 秒（原版 900ms）。
  时间预算只在搜索内部检查，战术判断和根节点排序会额外花一些时间，实际用时可能略长于设定值。
- 性能优化：评估函数中最频繁的“列出某方明子”查询改为按局面缓存（`Game.face_up_pieces`），
  搜索速度约提升 1.4~2 倍；已用固定随机种子、固定深度对比优化前后的选择，48 个局面结果完全一致。

## StrategicV16AI：精简新基线

V1~V15 是十几个版本叠加的补丁（约 830 个手调常数，近一半着法由绕过搜索的规则直接决定）。
V16 重新写了一个结构简单、便于调参和接入机器学习的基线（`fanfanqi/v16.py`），V15 保留作对照：

- **翻子按概率处理**：翻子 / 炮打暗子是概率节点，按剩余棋子池里各类棋子的数量加权平均，
  不再像 V14/V15 那样假设总能翻出对自己最有利的棋子。根节点精确展开所有可能结果，
  更深的翻子用近似（`full_chance_plies` 控制精确展开的层数）。
- **约 15 个有名字的评估权重**（`config.json` → `v16.weights`）：HP 差、明子战斗力、机动性、
  被威胁的棋子、未翻出的己方棋子、将的安全（敌兵距离、瞄将的炮、可逃格）、先手。
- **全部决策经过搜索**：迭代加深 Alpha-Beta + 只看吃子的静态搜索 + 置换表，没有规则覆盖。
- **目标函数**（`v16.multiplier_exponent` = λ，`v16.loss_aversion` = κ）：估算胜率
  p = sigmoid(评估分 / `win_temperature`)，局面价值 = (2p − 1) × 预估终局倍率^λ，结果为负时再乘 κ。
  λ = 1 最大化“胜负 × 倍率”的期望（领先时倾向把倍率做大，落后时倾向压小）；λ = 0 只追求胜率
  （同样能赢时仍略偏好大倍率）；0.3～0.5 即“优先赢，兼顾倍率”。κ > 1 更看重少输。
  旧配置里的 `objective: "reward" / "win"` 会自动换算成 λ = 1 / 0。
  预估终局倍率 = 连击系数 × (开局四子翻棋分 + 血量差)。
- **整数棋盘 + 原地走子/撤销**，与 `Game` 的规则经 4900 多个局面逐项比对一致（着法生成、HP、连击、倍率）。

`v16` 配置项：

| 键 | 默认 | 说明 |
|---|---|---|
| `multiplier_exponent` | `1.0` | λ：1 按倍率期望 / 0 只看胜负 / 中间值兼顾 |
| `loss_aversion` | `1.0` | κ：预计输时的放大系数，>1 更看重少输 |
| `win_temperature` | `12` | 评估分换算胜率的温度，越大胜率越保守 |
| `max_depth` | `8` | 迭代加深最大层数（通常先被思考时间限制） |
| `root_flips` / `node_flips` | `8` / `3` | 根节点 / 内部节点最多考虑几个翻子位置 |
| `node_quiet_moves` | `10` | 内部节点最多考虑几个非吃子着法 |
| `qsearch_depth` | `4` | 静态搜索最多连续几次吃子 |
| `full_chance_plies` | `1` | 前几层的翻子精确展开所有结果 |
| `weights.*` | 见 `v16.py` | 评估权重，单位约等于 1 点 HP |

对弈基准结果（每步 0.5 秒，各 30 局，红黑轮换，翻子结果随机；“倍率净得分”= 赢局倍率之和 − 输局倍率之和）：

| 对局 | V16 胜率 | V16 倍率净得分（场均） | 平均倍率 |
|---|---|---|---|
| V16（`reward` 目标）vs V15 | 73%（22 胜 8 负） | +458 | 755 |
| V16（`win` 目标）vs V15 | 93%（28 胜 2 负） | +538 | 620 |

两种目标都明显强于 V15。`reward` 目标确实把倍率做大了（平均 755 对 620），但多输了几局，
按倍率算的净得分反而略低于只看胜负的版本——说明“为做大倍率而冒的险”目前偏多，
`win_temperature` 等参数还需要调。30 局样本仍有随机误差。

运行基准（命令行用 `StrategicV16AI:λ` 或 `StrategicV16AI:λ,κ` 指定目标参数，`:win` 等同 `:0`）：

```bash
python -m tests.selfplay StrategicV16AI StrategicV15AI 30 0.5
python -m tests.selfplay StrategicV16AI:0 StrategicV15AI 30 0.5
python -m tests.selfplay StrategicV16AI:0.5,1.5 StrategicV16AI:1 30 0.5
```

## StrategicV17AI：V16 的搜索改进版

V17 复用 V16 的紧凑棋盘、评估权重、倍率目标和概率翻子搜索，并增加以下改动。V17 是当前默认模型，
V16 保留为对照基线；自对弈仍可用于评估后续策略调整。

- 根节点和内部节点中，吃子优先；之后交错搜索翻子和普通移动，避免一种着法因固定排序分数而长期排在队尾。
- 搜索中每 32 个节点检查一次时限，并在根节点每个候选着法前检查；超时时返回上一轮完整迭代的结果，
  如果连第一轮都没完成则返回一个合法候选着法。
- 静态搜索可选扩展炮打暗子概率分支（`q_hidden_depth`，默认 0 关闭）。实测打开后静态搜索开销过大、
  主搜索变浅，0.3 秒/步对 V16 只有 15 胜 37 负；关闭后炮打暗子仍由主搜索按剩余棋池精确展开。
- 静态搜索做差值剪枝：吃子后即使按“被吃棋子 HP + 子力 + `delta_margin`”乐观估计也无法超过 alpha 时直接跳过；
  能直接分出胜负的吃子总会搜索。
- 局面评估按（棋盘、棋池、HP、行动方）缓存，置换带来的重复局面不再重复计算。
- 炮的子力随局面变化：炮隔子吃子，棋盘越满炮架和目标越多，残局价值明显下降。
  满盘时取 `piece_value.炮`，空盘时取 `cannon_endgame_value`，按棋盘占用格数（明子 + 暗子）线性插值。
- 深层翻子是近似处理（不揭示棋子、棋盘不变），不同翻子位置得到的是同一个子局面，因此内部节点只保留一个。
- V17 保留 V16 的池子子力期望。HP 已包含棋盘和剩余棋池中的存活棋子，因此不再把池中 HP 重复加到评估分；
  炮打暗子的各个概率分支会直接更新 HP。
- 前期渐进加宽：棋池至少 20 枚时根节点最多看 6 个翻子位置，至少 12 枚时看 7 个，之后恢复为 8 个；
  内部节点的翻子宽度也随棋池缩小逐步恢复。大量暗子阶段对翻子和炮打暗子中的非将、兵结果做系统分层抽样，
  将、兵结果仍精确计算；同一局面的候选着法共用样本，减少比较时的随机误差。棋池少于 12 枚后恢复完整概率展开。

`v17` 配置独立于 `v16`，便于调节：

| 键 | 默认 | 说明 |
|---|---:|---|
| `q_hidden_caps` | `1` | 每个静态搜索节点最多扩展几个炮打暗子目标 |
| `q_hidden_depth` | `0` | 静态搜索中连续扩展炮打暗子的最大次数（0 = 不扩展） |
| `delta_margin` | `6` | 静态搜索差值剪枝的余量（HP），负数关闭 |
| `eval_cache_size` | `200000` | 每次搜索最多缓存多少个局面评估，0 关闭 |
| `cannon_endgame_value` | `2` | 棋盘全空时炮的子力；满盘时取 `weights.piece_value.炮`，按占用格数线性插值。负数则炮值固定 |
| `time_check_interval` | `32` | 递归搜索检查时限的节点间隔 |
| `early_pool_threshold` / `mid_pool_threshold` | `20` / `12` | 渐进加宽的棋池大小分界 |
| `early_root_flips` / `mid_root_flips` | `6` / `7` | 前期 / 中期根节点最多考虑的翻子位置 |
| `early_node_flips` / `mid_node_flips` | `2` / `3` | 前期 / 中期内部节点最多考虑的翻子位置 |
| `early_chance_samples` / `mid_chance_samples` | `6` / `8` | 对非关键翻子结果的系统分层样本数 |

对比命令示例：

```bash
python -m tests.selfplay StrategicV17AI StrategicV16AI 100 0.5
python -m tests.selfplay StrategicV17AI:0 StrategicV16AI:0 100 0.5
python -m tests.selfplay go/StrategicV17AI go/StrategicV16AI 100 0.3   # go/ 前缀使用 Go 引擎（单线程）
```

## Go 搜索引擎

界面可设置长捉与未吃子和棋阈值。修改后立即对当前局面生效，并写入 `config.json`。局面 v6 导出会记录阈值和累计连击分。

界面「计算引擎」可选 Python 或 Go；策略版本在「策略版本 / 模型」中选择。Go 版支持 V16、V17，
单线程时与 Python 版逐局面结果一致（固定深度下着法和分值相同），速度约快 50～100 倍。
多线程时每一层先由主线程搜上一轮的最佳着法定出 alpha，其余根着法再分给各线程，共享置换表和 alpha，
因此多线程结果可能与单线程略有不同。
需要本机安装 Go 1.21 或更高版本；首次选择 Go 时会自动编译，并把可执行文件缓存到系统临时目录。
设置环境变量 `FANFANQI_GO_BINARY=<路径>` 可指定一个已编译好的引擎（长时间跑基准时固定版本，不受源码修改影响）。
Python 界面、规则录入和其他旧 AI 模型继续由 Python 运行。

Go 引擎的实现要点：棋盘和棋池用 Zobrist 增量哈希；置换表是固定大小的数组（`tt_bits`，默认 2^21 项，
多线程共享）；走法列表按搜索层复用缓冲区，热路径不分配内存；搜索参数在建搜索器时一次性读出。
每步 2 秒、24 个测试局面上，V17 单线程平均 5.75 层，4 线程平均 6.17 层（暗子多的前期约 6 层）。

## 关于“模型”：目前没有训练出来的模型

现在的 AI（包括 V15）全部是**手写规则 + 搜索**：评估函数里的权重是原作者人工调出来的，
没有任何从数据里学到的参数，所以项目里只有代码、没有模型文件。原项目的 `training/` 目录
只提供了 PyTorch 训练脚本，仓库里也没有附带训练好的权重。

## 局面状态格式（训练样本 / 外部同步共用）

一个局面只需要“当前这一刻”的信息，不需要整盘棋谱。格式（`fanfanqi/state.py`，v6；v1~v5 文件仍可导入）：

```json
{
  "v": 6,
  "turn": "black",
  "hp": {"red": 41, "black": 53},
  "board": [
    ["b仕", "?" , "b兵", "?"],
    ["r炮", "." , "?" , "."],
    ["?" , "b兵", "?" , "."],
    ["b将", "?" , "r仕", "."],
    ["?" , "r马", "?" , "r象"],
    ["." , "b象", "?" , "r仕"],
    ["." , "?" , "r车", "?"],
    ["." , "r兵", "r炮", "b兵"]
  ],
  "captured": {
    "red":   {"象": 1, "车": 1, "马": 1, "兵": 2},
    "black": {"车": 1, "兵": 1}
  },
  "combo": {"red": 2, "black": 0},
  "max_combo": {"red": 2, "black": 1},
  "combo_score": {"red": 0, "black": 0},
  "flip_score": 32,
  "no_capture_plies": 3,
  "chase_count": {"red": 0, "black": 1},
  "chase_target": {"red": null, "black": 9},
  "rules": {"long_chase_limit": 5, "no_capture_limit": 16},
  "multiplier": {"combo_factor": 1, "flip_score": 32, "hp_diff": 12, "multiplier": 44}
}
```

| 字段 | 含义 |
|---|---|
| `turn` | 轮到哪一方走：`red` / `black` |
| `hp` | 双方剩余血量（红黑分数）。可省略，程序按 `captured` 推算：60 − 被吃棋子血量之和 |
| `board` | 8 行 × 4 列，行 0 在最上。`"?"` 暗子，`"."` 空格，`"r"`/`"b"` + 棋子类型表示红/黑明子 |
| `captured` | 双方**各自被吃掉**的棋子及数量（不是吃到的）。类型用 将仕象车马炮兵，也接受 帅相士卒 |
| `combo` | 双方当前连击数（v2，可省略，默认 0） |
| `max_combo` | 双方本局最高连击段长度（v2，可省略，默认 0；用于展示和旧版迁移） |
| `combo_score` | 双方已结束且达到 3 次的连击段分数之和（v6；旧版从最高连击估算一段，无法还原重复连击） |
| `flip_score` | 只累计开局放置的 4 枚明子；后续翻子不计（v4；旧版 v1~v3 导入时重置为 0） |
| `no_capture_plies` | 连续未吃子的普通移子数；翻棋不计，达到 `rules.no_capture_limit` 判和（v4；v1~v3 导入时重置为 0） |
| `chase_count` / `chase_target` | 双方当前长捉次数及对方明子目标格索引；达到 `rules.long_chase_limit` 时禁止继续追同一目标（v3） |
| `rules` | 当前局使用的长捉上限和未吃子和棋步数（v5；旧版用默认设置） |
| `multiplier` | 导出时附带的倍率明细，只供查看；导入时忽略，按上面各项重新计算 |

连击、开局四子翻棋分和新增规则计数无法从棋盘推出（它们取决于过程），所以要单独记录；其余信息都能推出，不必单独存：

- **剩余棋子池**（暗子可能是什么）= 全部 32 子 − 明子 − 被吃棋子；
- 一致性约束：空格数 = 被吃总数、暗子数 = 剩余池大小、血量 = 60 − 被吃血量。
  `game_from_state()` 会逐项检查，不自洽时给出具体原因（便于发现录入 / 识别错误）。

**机器学习特征**（`encode_features()`，643 维，特征版本 4）：前 608 维与原项目 `training/encode.py` 完全相同
（14 种明子 + 暗子 + 空格 + 走子方 + 双方 HP，共 19 个 8×4 平面）；之后 28 维是新增的
**双方被吃棋子数**和**剩余池各类型数量**（各 14 维，按该类型总数归一化）；最后 7 维是倍率相关：
双方当前连击（÷5）、双方累计达标连击分（÷16）、开局四子翻棋分（÷40）、血量差（÷60）、倍率（÷500）。
原编码看不出暗子里还剩什么，加上这部分后模型才知道“翻开大概率是什么”“对方还剩几个兵能威胁将”；
倍率相关的维度让模型能学到“领先时把倍率做大、落后时压小”。

## 倍率规则

倍率是每局的最终评分参数（训练用的奖励 = 胜负 × 终局倍率）：

```
倍率 = 连击系数 × (翻棋分 + 血量差)
```

| 组成 | 计算方式 |
|---|---|
| 翻棋分 | 只按开局放置的 4 枚明子计分：兵/卒 +2，车、马 +4，炮 +6，象/相 +4，仕/士 +8，将/帅 +12。后续翻棋、炮打暗子不计 |
| 血量差 | \|红方 HP − 黑方 HP\|，直接使用原始 HP；失败方为负数时也计入差值 |
| 连击 | 同一方连续自己的回合都吃到**对方的子**才累加，某回合没吃到对方棋子就结束本段；炮打暗子只在翻出对方棋子时计入 |
| 连击系数 | 每段达到 3 次的连击都计入该方累计连击分；双方累计分相加。当前连击段达到 3 次后实时计入，段结束后保留；尚无达标连击段时系数为 1 |

例：红方先后两段 3 连击、黑方一段 4 连击，连击系数 = 3 + 3 + 4 = 10。开局四子翻棋分 32，红 24 / 黑 0 HP → 倍率 = 10 × (32 + 24) = 560。
界面右侧「倍率」面板实时显示双方累计连击分；当前连击段达到 3 次后会实时计入。

## 长捉与和棋规则

- 同一方连续追同一枚对方明子时累计长捉次数；第 5 次仍追同一目标的走法不合法，必须变招。吃子、翻子、停止追击或改追其他目标会重置/重新计数；炮打暗子不作为长捉目标。
- 连续达到设置的未吃子步数判和（默认 16 个普通移子）。翻子不计步、不改变计数，任何吃子（包括炮打暗子）清零计数。
- 规则计数会随悔棋恢复，并包含在 v6 局面导入/导出数据中。旧版未吃子计数和翻棋分会重置为 0；旧版中已有的长捉计数会保留。

## 自学习迭代路线

推荐分阶段进行，每一步都用对弈基准验证确实变强了再进入下一步：

1. **生成数据**：`python -m tools.gen_data --games 1000 --engine go --workers 8 --think 0.3`
   （`--engine go` 用 Go 引擎，`--workers` 多进程并行，建议不超过物理核数；AI 参数读 `config.json` 的 v16 / v17 段）
   每个局面一行 JSONL：`{"state": {...}, "move": {...}, "result": 1, "reward": 550, "final_multiplier": 550, "ply": 12,
   "final_hp": {...}, "model": "StrategicV17AI", "state_version": 6, "feature_version": 4, "game": "..."}`。
   `result` 是从“轮到走的一方”看的最终胜负（赢 1 / 输 −1 / 和 0），`reward` = `result` × 终局倍率，
   `move` 是 AI 在该局面的选择；`model` 和两个版本号用于区分不同策略 / 编码生成的数据。
   `--epsilon` 控制混入随机着法的比例，让数据覆盖 AI 自己不会走到的局面。
2. **训练价值网络**：输入 643 维特征，用 `reward`（或只看胜负时用 `result`）做标签。小型 MLP（636→128→64→1）即可，
   CPU 上用 numpy / PyTorch 都能训练。暗棋有运气成分，标签噪声大，需要上万个局面以上。
3. **接入搜索**：把网络输出按一定权重加到 V17 的局面评估（`Searcher.leaf_value`）上，保留原有搜索。
4. **验证**：`python -m tests.selfplay 新模型 StrategicV17AI 200 0.3`，胜率明显高于 50%（例如 >55%）才采用。
5. **迭代**：用新 AI 自对弈生成新数据 → 重新训练 → 再验证，循环往复（专家迭代，AlphaZero 思路的简化版）。
   之后还可以用 `move` 字段训练策略头，用来给搜索排序着法，同样时间内搜得更深。

### 不上神经网络：Texel 调参

V16/V17 的评估分本身就是各评估项的线性组合（`Searcher.eval_terms` 导出特征，满足
Σ 权重 × 特征 = `static_eval`，`tests/selfplay` 会校验），所以可以直接用自对弈胜负拟合权重：

```bash
python -m tools.gen_data --games 1000 --engine go --workers 8 --out data/round1.jsonl
python -m tools.texel data/round1.jsonl                    # 只看结果
python -m tools.texel data/round1.jsonl --apply            # 验证集损失下降才写回 config.json
python -m tests.selfplay go/StrategicV17AI ... 200 0.5     # 新旧权重对打，赢了才保留
```

- 只用安静局面（轮到走的一方无子可吃），按对局划分训练 / 验证集，`--l2` 把权重拉向当前值防止跑偏，
  `--fix` 指定保持不变的权重（默认 `tempo`）；
- 炮的动态子力拆成 `piece_value.炮`（满盘）和 `cannon_endgame_value`（空盘）两项，一起拟合；
- 每局约 50 个局面，其中约一半是安静局面，1000 局约 2 万多个样本，够拟合这十几个权重；
- 写回配置后，下一批 `gen_data` 自动用新权重生成，循环即可分批迭代。

## 同步外部棋盘 / 识别结果

要让 AI 给“别的棋盘”（实体棋盘拍照、其他软件）出提示，关键是把识别结果转成上面的状态格式，
再用「导入局面」或 `game_from_state()` 载入：

1. **识别棋盘**：定位 4×8 的格子（透视校正），对每格分类为 16 类：空、暗子、红/黑各 7 种明子
   （可以用模板匹配汉字 + 颜色，或训练一个小 CNN）。
2. **被吃棋子**：识别棋盘外的弃子区；如果无法拍到，可以连续跟踪画面，由前后两帧的差异推断谁被吃了，
   或者让用户手动补录。
3. **轮到谁**：由用户指定，或根据连续跟踪的着法交替推算。
4. **校验**：`game_from_state()` 会检查数量、空格 / 暗子、血量是否自洽；识别错误通常会在这里暴露，
   出错时让用户纠正对应格子即可。
5. **增量同步（后续可做）**：比较前后两个状态推断出实际着法（`?`→明子是翻棋，A 空 B 有子是走子 / 吃子），
   然后用 `flip_piece` / `move_piece` 执行，这样能保留走子历史（AI 的“防来回走”判断会用到）和棋谱。
   目前的「导入局面」是整局面覆盖，最简单稳健，但不带历史。

对接方式上，现在是通过 JSON 文件导入；如需实时同步，可以再加一个本地 HTTP 接口或监视某个文件夹，
识别程序写入新状态后界面自动刷新并给出提示。
